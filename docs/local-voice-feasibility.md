# Local voice without ElevenLabs

[Issue #10](https://github.com/markdlabrecque/shepherdr/issues/10) · Source review at `89f501bb` and upstream API review only. No speech server or device trial.

**Go on dictation.** Start with opt-in, local upload-at-Done on desktop and web/mobile. Add streaming once the batch path is reliable. **Conditional go on calls.** Use self-hosted speech recognition and Kokoro, but let Shepherdr run the conversation. Desktop and foreground web/mobile calls are plausible; full duplex depends on the client's echo cancellation. Reconnect and Android Wake handoff are feasible to preserve at the protocol level, subject to a real phone test. A browser-only call cannot promise a live mic or socket while the OS suspends it. No-go on replacing just the ElevenLabs URL.

## What ElevenLabs does today

| Path | Current behavior and replacement boundary |
| --- | --- |
| Desktop dictation | [`Dictation.stop()`](../mods/chat/dictate.js) asks [`record.ts`](../mods/chat/record.ts) to stop the default mic. The helper sends 16 kHz mono PCM to Scribe over an API-key WebSocket and writes a temporary WAV and, on success, a text sidecar. Otherwise [`transcribe.ts`](../mods/chat/transcribe.ts) uploads the WAV. Cancel discards the result; Done puts editable text in the composer, never sends it. |
| Web/mobile dictation | [`dictate()` and `liveSession()`](../web/src/dictation.ts) use `getUserMedia`, AudioWorklet PCM and a direct Scribe WebSocket with a single-use token from `POST /api/dictate/live`. The in-memory MediaRecorder capture goes to `POST /api/dictate` if live fails. [`dictate()` / `liveToken()` on the service](../service/dictate.ts) share the voice key. [`core/voice.js`](../core/voice.js) binds `transcribe()` to Scribe v2 multipart `{file, model_id, …}` → `{text}` (20 MiB, 60 s), and `liveUrl()` / `liveChunk()` / `liveWords()` to Scribe v2 Realtime's base64 PCM16 and manual commit (400 ms silence tail, 4 s wait for final text). Both paths recognize while recording, but insert text at Done. |
| Desktop calls | [`mods/chat/voice.ts`](../mods/chat/voice.ts) is a Bun helper spawned by the chat mod. `main()` opens its own signed ElevenLabs socket; the window uses call-folder state, mute/end commands and `nav`/`navved` files. `serviceTool()` / `hear()` use checked loopback and a local token for `/api/voice/tool` and `/api/voice/hear`. Without the service the helper still calls ElevenLabs, but `localTool()` can only read and send to the originating chat. [`callAudio()`](../mods/chat/audio.ts) uses macOS voice processing for echo cancellation and slight ducking; PipeWire or macOS fallback mutes the input during playback and briefly after. `hush()` drops queued audio on interruption. |
| Web/mobile calls | [`call.ts`](../web/plugins/voice/call.ts) sends binary 16 kHz mono PCM to the same-origin `/api/voice` socket and plays PCM back. [`voiceCall()`](../service/voice.ts) dials ElevenLabs, wraps input as base64 JSON, unwraps output, checks output format, answers pings and translates transcript/response/interruption/tool events to client state, `interrupt`, navigation or audio. `CallDeps.dial` swaps a socket address in tests, not a protocol. The browser requests echo cancellation and noise suppression. Its audio unlock, `play-and-record` where available, media element, Media Session controls and mic reacquisition are best-effort client behavior. |

`ensureAgent()` / `agentSpec()` provision and update the remote “Herdr chat” agent. Its signed conversation socket starts with `opening()`, including app context. ElevenLabs owns recognition, endpointing, the tool-capable LLM and conversation history, pre-tool speech and typing sounds, the slow-answer cue, speech generation, language switching and interruption detection. The spec disables spoken idle prompts, ends after 30 minutes of silence or two hours total, and asks for no voice recording and zero retention. `skip_turn` and `language_detection` are ElevenLabs system tools; Shepherdr handles `hang_up`, not the built-in `end_call`. The existing `hangUpGuard()` checks for a prior question and a fresh transcript with no intervening tool; the prompt/model interprets the yes. The guard itself does not verify assent.

Shepherdr already owns the tools. [`voiceTool()` / `shown()`](../service/voice-tools.ts) implement `look` (including cross-machine app data, chats and secret names, not values), `send` (as the person), `act` (requires the model's `confirmed: true`), `open`, `screen` and web-only `call_view`. `open`/`screen` need acknowledgement from the attached client before claiming success. Browser DOM refs and [desktop frame refs](../mods/chat/call-screen.js) are client-specific. Risky screen clicks have confirmation checks. [`hearing()`](../service/voice-hear.ts) follows the on-screen chat, chats the call sent to and fresh requests for attention. `turnGate()` and the quiet window put the person's turn first and batch updates. `talking()` is an RMS gate for those updates, not the call's end-of-turn detector.

On a dropped web socket, the service holds the conversation in memory for 60 s; the browser retries for about 55 s with the call ID. `attach()` checks ownership through `callToResume()`, replaces the attached client and asks the agent to recap missed speech after a gap. This is not recovery from a dead ElevenLabs socket or service restart. On lock, Shepherdr Wake can `POST /api/voice/handoff` from the same authenticated tailnet device, take over via `/api/voice?resume=<id>`, and report `locked`/`screen`. The page stops its mic and playback without ending the call and offers Take it back. Wake is a separate client; preserve the wire contract and test its navigation and locked-screen capabilities rather than inferring them from web tests.

## Speech servers worth trying

| Candidate | Upstream contract | Fit and limits |
| --- | --- | --- |
| [Speaches](https://github.com/speaches-ai/speaches/tree/993994f7984bf3fe9655b267448328cf66fccb42), faster-whisper STT | `POST /v1/audio/transcriptions`, multipart `file` + `model` → JSON `{text}` or SSE segments from an uploaded file. [Realtime transcription-only](https://speaches.ai/usage/realtime-api/) accepts base64 PCM16 in `input_audio_buffer.append`; [the pinned decoder](https://github.com/speaches-ai/speaches/blob/993994f7984bf3fe9655b267448328cf66fccb42/src/speaches/realtime/input_audio_buffer_event_router.py) takes 24 kHz and resamples to 16 kHz. VAD or commit produces completed transcripts per utterance. Do not assume stable word-by-word partials or equate upload SSE with a live mic. | First choice on Linux/CUDA for batch and utterance-based live STT. Optional server API key; CPU images exist, but upstream warns that conversational realtime performance needs CUDA and a fast LLM. Defaults include an English-only STT model; explicitly choose a multilingual Whisper checkpoint for language detection. Speaches and upstream Whisper code/weights are MIT; verify the selected conversion's license. Model residency, workers and concurrent calls need measuring. |
| [whisper.cpp `whisper-server`](https://github.com/ggml-org/whisper.cpp/tree/6680804f99c3982b7d59f27ae315ce880570017e/examples/server) | Multipart WAV `file` to `/inference` → JSON with `text`; optional FFmpeg conversion. Its separate `whisper-stream` mic example reruns inference on windows; the HTTP server is not a streaming mic API. | First batch choice on an Apple Silicon or CPU-only host. CPU, Metal/Core ML and CUDA paths. Upstream lists base/small at about 388/852 MB model memory before app/concurrency overhead. MIT. Keep the example behind Shepherdr; do not expose `/load` or arbitrary uploads. |
| [Vosk Server WebSocket](https://github.com/alphacep/vosk-server/tree/47998a26f232252f7baaed53dd8ce89d38bbfbce/websocket) | Set sample rate, send binary mono PCM16 (use 16 kHz), get `{partial}` or `{text}`; `{"eof":1}` flushes the final result. This is incremental decoding, not repeated batch inference. | CPU fallback if Whisper endpointing or partials disappoint. One recognizer per socket and a CPU-sized worker pool; cap clients at the proxy. The example socket has no auth. [Models](https://alphacephei.com/vosk/models) are language-specific and separately licensed; small English US is Apache 2.0, 40 MB, with roughly 300 MB runtime memory typical for small models. Compare accents, project names and mixed language before choosing it. |
| [Kokoro-FastAPI](https://github.com/remsky/Kokoro-FastAPI/tree/ffa06918946413667af51e8c3459e598dc78fdf0) | `POST /v1/audio/speech` JSON `model`, `voice`, `input`, `response_format: "pcm"` → streamed 24 kHz mono PCM16. Its TTS-only WebSockets are not `/convai`: the Cartesia-compatible socket documents per-context cancel; ElevenLabs-compatible `close_context` finishes pending text. | Preferred dedicated TTS API. Start with HTTP per short phrase; verify abort behavior before choosing the cancel-capable socket. Optional `API_KEYS` (off by default), CPU and CUDA images, native Apple MPS. Apache-2.0 wrapper and [Kokoro 82M v1.0 weights](https://huggingface.co/hexgrad/Kokoro-82M). Pick voices by language. English (US/UK), Spanish, French, Hindi, Italian, Japanese, Brazilian Portuguese and Mandarin are documented; no Swedish voice documented. |
| [Speaches Kokoro ONNX](https://github.com/speaches-ai/speaches/blob/993994f7984bf3fe9655b267448328cf66fccb42/docs/usage/voice-chat.md) | Same `/v1/audio/speech` shape with a Kokoro model ID and voice, streamed `audio/pcm` with optional output rate. The pinned Kokoro executor generates at 24 kHz; verify framing and output rate on the deployed build. | One service for both speech tasks on Linux if it passes the same quality and cancel checks; choose the exact ONNX model/license and voice set before shipping. Simpler to run, but STT and TTS can contend for resources. Speaches' conversational WebSocket documents no `response.cancel` or `conversation.item.truncate`; don't put it in charge of calls. |

Use upstream memory figures as planning hints, not sizing promises. Measure peak RAM/VRAM, cold vs warm startup and two simultaneous sessions on the intended host before setting limits. Pin server builds and model revisions, check licenses and hashes. Kokoro cannot reproduce the current voice or broad language switching. Start calls in English with an explicit supported-language/voice list; tell the user when a voice is unavailable. Dictation can still use multilingual STT with no TTS requirement.

## Where to put the new code

```text
Browser/Wake --HTTPS/WSS--> Shepherdr service --+
Desktop audio helper --authenticated local------+--> call engine --> private STT and Kokoro
                                                                  --> text-only LLM
                                                                  --> Shepherdr tools --> client nav/ack
```

Use independent speech adapters: batch transcription, live PCM with final/flush/cancel, and streamed synthesis with an abort signal. Keep the clients' PCM16/16 kHz call contract; resample and frame at the adapter, including Kokoro's 24 kHz output. For local dictation, proxy web live audio over an authenticated same-origin socket, replace provider tokens with Shepherdr session setup, and keep batch fallback on the **same local provider**. Preserve the desktop helper and add a local-service route for shared tools. Share the call engine with a helper-hosted mode for service-less desktop use, with only originating-chat read/send, rather than silently losing today's fallback. Dictation never needs the reasoning model.

Keep call identity, in-memory history and the one active attachment in Shepherdr. The call engine owns VAD/endpointing, the streaming tool-capable text LLM, short speech chunks, pre-tool cues, quiet-time updates and idle/end timers. On barge-in, cancel text/TTS work, emit `interrupt`, drop queued/late frames by turn ID and do not treat unheard speech as delivered. On reconnect or handoff, fence off old audio and nav acknowledgements, keep context, and recap what may have been missed. Do not replay a `send` or mutation on retry. Use a bounded queue, deadlines and release/cancel on End. Bind a fresh, explicit user confirmation to the proposed action and target (including hang-up); a model flag, tool result or detached client must not authorize it. Start read-only and keep current app auth and acknowledgements as the authority. A [Pipecat](https://github.com/pipecat-ai/pipecat) sidecar could supply VAD and speech pipeline pieces later, but still needs a bridge for Shepherdr tools, attachment ownership and Wake. Keep those in Shepherdr rather than introducing another session owner up front.

Local means audio stays on the user-controlled path, not necessarily on the phone. A phone's `localhost` is the phone; direct speech-server access adds reachability, browser mixed-content/CORS and credential problems. Keep the existing tailnet/origin and loopback gates; put speech endpoints behind a private ACL or on loopback, use TLS/auth across hosts, and accept only administrator-set destinations with redirect and address checks. Never forward the Shepherdr token or ElevenLabs credentials. Limit uploads before decoding and isolate media conversion. Minimize and redact transcripts, tool output and app context sent to an opt-in cloud LLM; that provider can still see the remaining text. Keep buffers/history ephemeral, clean up desktop temp files, and disable payload logging on service, proxy and inference workers. Intentionally sent chat messages keep their normal chat history. Show provider and reachability in Voice settings; keep ElevenLabs opt-in/selectable for existing users, with its usage row only when applicable. Local mode needs no ElevenLabs key or agent ID and fails visibly rather than falling back to cloud speech.

## Later validation and estimates

Human engineering time, excluding hardware procurement or a new native client. Each stage depends on the preceding checks passing. Start with synthetic audio and fake endpoints; real inference and phone audio trials need separate authorization.

1. **Batch dictation, 12–18 h.** One real vertical slice on desktop and web, then provider selection, packaging/shared-copy checks and docs. Verify native WAV and browser WebM/Ogg/MP4, editable draft/no autosend, Done/Cancel, empty speech, malformed output, auth failures, oversized input and server timeout. Extend `service/dictate.test.ts`, `core/voice-live.test.js` as appropriate, and `web/src/dictation.test.ts`.
2. **Live dictation, 12–18 h.** Test partial/final reconciliation, finish flush, short/long utterances, cancellation/backpressure and a local-only upload fallback. On the intended host, measure p50/p95 first usable transcript and Done-to-text against the current UX, cold/warm and with two sessions. Use accented synthetic speech, silence and project names in English and Swedish. If useful partials or final latency miss the agreed target, keep batch enabled and live optional.
3. **Foreground calls, 32–48 h.** First read-only on web and desktop, then gated write tools. Extend `service/voice-call.test.ts`, `voice-tools.test.ts`, `voice-hear.test.ts`, `core/voice-spec.test.js` and `web/plugins/voice/call.test.ts`. Cover quiet updates, slow tool cues, nav ack/timeout, confirmation and hang-up refusal, canceled speech, late packets, no duplicate mutations, crashes and no silent fallback. On real hardware check end-of-speech to first audio, barge-in to silence, Mac ducking and echo, and Linux/macOS half-duplex fallback under load. Use Chromium automation and a manual Firefox check for permission, autoplay and echo; automation cannot establish acoustic performance.
4. **Phone continuity and privacy gate, 16–24 h.** Extend `service/voice-wake.test.ts` and the call tests for hold expiry, one active attachment and lost upstream. On actual iOS Safari and Android with Wake, try lock/unlock, Siri/phone interruptions where applicable, mic loss, Wi-Fi/cellular changes, Wake Take it back, and locked navigation, mute and End. Reject full-call parity if handoff drops context, takes the wrong mic or repeats an action. Inspect logs and allowed outbound traffic with dummy data; prove no audio leaves the private path and confirm what cloud text is sent. Then consider wider opt-in.

Total: **72–108 h**. Mocks can prove protocol behavior and cancellation ordering, not recognition accuracy, playback latency, acoustic echo or OS suspension behavior.
